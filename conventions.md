## Цель

Чат-приложение в стиле Telegram. Слева — единый список чатов: личные диалоги, группы и каналы идут на одном уровне (как в Telegram, без вложенности). Справа — сообщения выбранного чата. Требование преподавателя — три клиента: веб-браузер, мобилка, десктоп.

## Терминология

- «Чат» — любой элемент списка слева: диалог, группа или канал.
- «Канал» — только broadcast-канал (пишут админы, остальные читают), не синоним чата.
- В коде универсальный контейнер сообщений называется `Channel` (как в Slack) — это чат любого вида, не только «канал» в телеграм-смысле.

## Архитектура

- **Бэкенд** — этот проект (папка `chatapp`), REST API + авторизация.
- **Фронтенд** — отдельный проект на Flutter: веб + мобилка из одной кодобазы.
- **Десктоп** — пока не решено (TBD). Кандидаты: Flutter Desktop (тот же код, что и мобилка), либо отдельная обертка позже. Разбираемся, когда заработает веб.

## Авторизация

- Идентификация пользователей обязательна — без неё нет смысла в каналах и авторах сообщений.
- Делаем на Spring Security.
- Формат: JWT в заголовке `Authorization: Bearer ...` (решено).

## Предварительная модель данных

- `User` — id, username (уникальный, для логина), пароль (хэш), отображаемое имя.
- `Channel` — универсальный чат (см. Терминологию): id, название, тип, участники (связь many-to-many с User).
  Типы (`ChannelType`), соответствуют трём видам записей в списке Telegram:
  - `DIRECT` — личный диалог (2 участника);
  - `GROUP` — групповой чат (пишут все участники);
  - `CHANNEL` — канал/broadcast (пишут админы, остальные подписаны и только читают).
- `ChannelMember` — участник чата: channel_id, user_id, role. Роли: `ADMIN` (пишет в каналах, управляет составом канала) / `MEMBER`. Владельца как отдельной роли нет — это `created_by` у Channel. В `DIRECT` роль не значима (всегда `MEMBER`).
- `Message` — id, channel_id, author_id, текст, время отправки.

Правила «кто может писать» (решено):

- `DIRECT` — оба участника.
- `GROUP` — все участники; добавлять участников может любой (права админов в группах отложено — роль уже хранится, фактические права добавим позже).
- `CHANNEL` — пишут только `ADMIN`; подписаться (стать читателем `MEMBER`) может любой авторизованный пользователь — подписка это та же запись в `channel_members`.

## API — общие правила

- Префикс `/api`, версия в пути пока не нужна (`/api/v1` — когда понадобится).
- JSON в обе стороны, имена полей — `camelCase` (как принято в Kotlin/Java-мире и удобно парсить во Flutter).
- DTO для входа/выхода на границе API, entity не отдаем наружу.
- Время — ISO 8601 в UTC.
- Ошибки — понятный JSON с кодом и сообщением, не голый стектрейс.

## Правила разработки

- Комментарии в коде — только где действительно неочевидно, код и имена должны объяснять сами себя.
- Новые зависимости — через обсуждение, не молча.
